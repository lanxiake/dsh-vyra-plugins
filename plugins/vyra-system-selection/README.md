# vyra-system-selection · 系统级划词

在**任何应用**里选中文字，松手即弹出横向菜单：AI 搜索、翻译、总结、解释、复制。

## 用法

选中文字松手 → 菜单出现在光标旁 → 点一个动作。**不用点右键。**

菜单是横向一条，图标在左、文字在右，每项宽度跟着自己的文字走：`[🔍 AI 搜索] [翻译] [总结] [解释] [复制]`（和豆包那类划词工具条同一个形状，一行高，不挡正文）。

- **选中即弹**（默认开启）。拖选一段文字、双击选一个词、三击选一行，松手就弹。
- **右键仍然可用**，弹的是同一个菜单 —— 谁也不必为了继续用而先学会新手势。
- **关掉菜单后，同一段文字不会原地重弹**。换一段新文字、或者重新右键，才会再弹。
- **取代了应用自带的右键菜单**（这是刻意的：同一个右键，两种结果会让人不知道该等哪个）。
- **没选中文字时右键**，仍然弹出应用原本的菜单 —— 点在链接、输入框或空白处时你想要的是那个。
- **DSH 窗口内同样可用**：选中回答或消息里的文字，松手即弹菜单。
- **点别处自动关闭**：菜单和结果面板都会在点击外部时收起，那一下点击**不会被吞掉**，照常传给下面的程序。
- 选中的文字进了剪贴板**也会被还原**，不会污染你原本复制的东西。
- **单击不取词**：只有拖动选中或双击/三击这种「可能真的选了字」的手势才会发 Ctrl+C 读剪贴板。单击只是放光标，去读它只会白白卡住输入 220 毫秒 —— 那正是「装上之后鼠标有点卡」的来源。
- **复制结果**：结果面板右下角的「复制」把答案正文（不含来源链接）放进剪贴板，底部会显示「已复制到剪贴板」；剪贴板被别的程序占住时会显示失败原因，而不是假装成功。
- 菜单**不抢焦点**：点它不会让被读取的应用失去选区。
- **跟随系统主题**：浅色系统用浅色菜单。
- 终端里用 Ctrl+Insert 而不是 Ctrl+C 取词，避免给你的进程发 SIGINT。

设置页：侧边栏 **设置 → 系统级划词**。可以关掉、改翻译目标语言、选模型、调检索条数，也可以关掉「划选后自动弹出」（默认开启，关掉后只剩右键）。

还能关掉 **接管右键菜单**。这是插件里唯一伸进系统输入链的部分：全局鼠标钩子让每一个鼠标事件都先进这个进程。嫌鼠标手感变钝就关掉它 —— 代价是**其他程序里右键不再弹我们的菜单**（DSH 窗口内照常，划选自动弹出也不受影响）。

钩子装上时，Windows 只在本进程抽消息队列的那一刻才把鼠标事件交出去，所以抽队列的间隔**就是**给全系统鼠标加的延迟。这里按 4ms 抽（平均多 2ms），只在弹窗可见、没装钩子时才降到 16ms —— 一帧就够了。

设置页的「运行状态」会显示当前**实际加载的版本号**：装完没重启时，磁盘上是新版本、这里还是旧版本号，一眼就能看出来。

### 点了没反应时看哪里

结果面板不再留空白：模型没输出正文、只返回了思考过程、流里根本没有文本块、选不到模型、枚举模型时抛错 —— 每一种都会在面板底部写明，而不是静静地什么都不显示。

设置页底部的 **最近一次调用** 会列出动作、模型、耗时，以及模型实际吐出的块（文本 / 思考 / 其他）；同样一份记录写在 `~/.dsh/storages/system-selection/last-run.json`。`文本 0 段` 而 `思考 N 段` 就意味着这个模型把预算全花在思考上了。

## 为什么不照抄 lumii

lumii 的划词**只是应用内 DOM 实现**（`window.getSelection()` + 渲染进程里的浮层），它的设计文档明确把系统级划词列为「独立特性，不是应用内版的增量」并后置了。所以能借的是它的**判断**，不是代码：

| 借来的 | 出处 |
|---|---|
| 锚点取选区**最后一行**的矩形，不是整个包围盒（否则多行选区时浮条会飘到第一行去） | lumii `snapshot.ts` |
| 先测量再定位，测量前 `visibility:hidden`，避免 0,0 处闪一帧 | lumii `SelectionToolbar.tsx` |
| 浮条只做 opacity 动画，不做 transform（scale 会让 `getBoundingClientRect` 量错） | lumii `SelectionToolbar.module.css` |
| 边缘翻转 + 夹紧到工作区 | lumii `floating-position.ts` |
| **不要持有活的 Range**，一切量完就转成普通数字 | lumii `snapshot.ts` |
| 超长直接**拒绝**而不是截断（截断后的翻译是错的，比报错更难发现） | lumii `selection-llm.ts` |
| 按下时 `preventDefault` 保住选区 | lumii `useSelectionWatcher.ts` |

换掉的部分：整个触达面和整个弹窗层。

## 架构

DSH 的插件宿主是一个 **Electron Node 模式子进程**，拿不到 `BrowserWindow`，Electron IPC 也有严格白名单 —— 弹窗做不了。

但那个进程里 **koffi FFI 可用**（DSH 自己用它做 Windows ACL 沙箱）。所以：

```
Host 进程 (vyra-system-selection)
├── 触发       WH_MOUSE_LL 钩子：拦右键、吞掉、换成自己的菜单
├── 预取       左键释放时读一次选区，缓存起来
├── 取词       SendInput(Ctrl+C) → 剪贴板 → 还原
├── 弹窗       真·Win32 窗口 + GDI 绘制（PeekMessage 泵在 Host 事件循环上）
└── 动作       ctx.llm.stream() / ctx.web.search()
```

**为什么必须用钩子**：要顶掉应用自带的右键菜单，没有别的办法 —— 没法请任意一个程序「让开」，只能在点击送达之前吞掉它。代价是回调必须在 Windows 的 `LowLevelHooksTimeout`（默认 300ms）内返回，否则系统会**静默摘掉钩子**。所以回调里只做判断，取词放到左键释放时预取（`captureSelection` 要 100–300ms，远超预算）。

**为什么自动弹出用轮询**：拖选/双击的「松手」这一刻要判定，而钩子回调的预算（Windows 的 `LowLevelHooksTimeout`，默认 300ms）不该为它多担一份风险——钩子里的判定必须只读缓存、立刻返回。轮询（`GetAsyncKeyState`，30ms）跑在普通事件循环上，等得起这 110ms 的取词延时。

钩子在同一个左键松手时已经取过一次词（存进 `lastSelection`），自动弹出**直接复用那份缓存**（`freshSelection`，只认 400ms 内的），所以一次手势只注入一次 Ctrl+C。

### 应用内（DSH 窗口内）划词

DSH 窗口内的**两条路都不走钩子** —— 钩子看到鼠标落在自己进程的窗口上就放行，事件照常送达浏览器。

- **右键**：渲染半边的 `contextmenu` 监听器接管。
- **选中即弹**：`pointerup` 监听器接管。用 `pointerup` 而不是 `selectionchange`：后者在鼠标还没松开时就连续触发，菜单会在拖选途中冒出来、然后一路追着选区跑。

两条都已有 `window.getSelection()` 和 `MouseEvent.screenX/screenY`，所以选区文本和屏幕坐标都是现成的，**不需要剪贴板往返，也不需要坐标换算**。判定「自动弹出是否开启」留在 Host（设置存在那边，渲染半边没有副本），渲染半边只管把 `auto: true` 报上去。

系统级那条路（钩子 + 轮询）会**跳过 DSH 窗口**：那是 Chromium 渲染进程，会忽略注入的 Ctrl+C，在那儿取词只是白等 220ms。所以窗口内的划选必须由页面半边接。

三条路径汇到同一个 `openInApp` / `onRightClick` → `showMenu`，所以菜单、动作、结果面板完全共用。

有一条刻意的例外：**选中输入框或内容可编辑区域里的文字时不接管**。在输入框里右键是要剪切/粘贴，浏览器自带的菜单才是有用的那个。

### 主题

菜单跟随 Windows 的应用主题（注册表 `AppsUseLightTheme`），浅色系统用浅色配色。用这个键而不是 `SystemUsesLightTheme`：后者只管任务栏，用户可以深色应用配浅色任务栏。

主题在**每次弹出前重读**，弹出期间约每秒复查一次，所以切换主题不需要重启也不需要重新加载插件。

**为什么用原生窗口而不是 Chromium**：插件宿主里没有 BrowserWindow，要 Chromium 就得再塞一个浏览器进来。分层 Win32 弹窗启动是微秒级、永不抢焦点、零安装。

### 弹窗位置怎么定

菜单和面板都挂在**选区矩形**上，不挂在鼠标上。

这不是细节：鼠标停在拖选的**终点**，从左往右选和从右往左选会落在选区的两端。挂在鼠标上时，右往左选会让菜单从选区右端往右下展开，正好压住选区下方的文字——而且两个方向表现不一致。

客户端用 `getRangeAt(0).getBoundingClientRect()` 量出选区，再换算到屏幕坐标：

```js
const originX = event.screenX - event.clientX   // 视口原点，精确
```

用 `screenX - clientX` 而不是 `outerWidth - innerWidth`，因为后者给的是**边框总量**，拆不出哪部分是标题栏、哪部分是边框——差几像素就是菜单压字的区别。

定位规则：

| 窗口 | 位置 | 理由 |
|---|---|---|
| 菜单 | 选区**下方**，水平居中；下方放不下才翻到上方 | 短，不挡阅读 |
| 面板 | 选区**下方**，答案与原文对照看 | 对照是面板存在的意义；下方放不下才翻上方 |

侧边**开面板时定一次、之后不再变**。流式回答会让窗口长高几十次，每次都重算就会让面板在选区两侧来回跳。下方时顶边固定向下长，上方时底边固定向上长。

## 开发

```sh
./verify-run.sh          # 或 DSH_EXE=/path/to/客户端 ./verify-run.sh
```

34 项测试，覆盖**纯逻辑**：提示词组装、菜单几何与命中、设置持久化、页面内选区判定、导入完整性（少 import 一个名字会让 Host 在用时崩掉）、重复导入不重复注册（koffi 类型名是进程级的）、取词门控（单击不取词）。都不碰鼠标、剪贴板和真实窗口。

跑它需要本机的 DSH 桌面端：脚本用 `DSH_DESKTOP_NODE_EXECUTABLE` 指到 `DeepSeek Harness.exe`，以 Electron 的 Node 模式跑 `--test`。路径写死在脚本里，换机器要改第一行的 `DSH=`；`test/` 与 `verify-run.sh` 都不随包发布（见 `files`）。

**碰桌面的部分靠手动验证**，没有自动化。曾经有过合成鼠标的 e2e，删掉了：它抢占真实的鼠标和焦点，跟机器上别的程序打架，然后把这种冲突报成失败 —— 一个既不可信、又会打断你正常使用电脑的测试，比没有测试更糟。

手动验证清单：

1. 任意应用选中文字松手 → **不点右键**，菜单就弹出、精确跟随光标、**应用自带的菜单不出现**
2. 任意应用选中文字 → 右键 → 同样弹菜单（右键这条路没被新手势挤掉）
3. 关掉菜单 → 同一段文字不会原地重弹；重新拖选同一段 → 会弹
4. 五个动作各点一次
5. AI 搜索：等来源列表出现，点来源能打开浏览器
6. 不选文字时右键 → 应用自己的菜单照常弹出
7. 点菜单外面 → 收起，且那一下点击传给了下面的程序
8. DSH 窗口内选中文字松手 → 弹菜单；右键 → 同样弹菜单
9. 切换系统主题（设置 → 个性化 → 颜色）→ 菜单跟着变
10. 设置页开关一次插件 → 关掉后右键不再被接管（验证钩子确实卸载了）
11. 按住 Ctrl 点右键 → **不弹菜单**，且随后 Ctrl+V 粘出来的还是你之前复制的东西（验证取词没有插手用户的组合键）
12. 终端里选一段文字松手 → 菜单弹出，且**没给你的进程发 SIGINT**（这条走的是 Ctrl+Insert 路径）

`packages/system-selection/native.js` 里有几个**只在 Windows 上运行**的绑定，改它们之后务必手动过一遍上面的清单。

### 排障

`POST /api/system-selection/rpc` `{"op":"status"}` 返回计数器，能看出卡在哪一步：

```json
{"stats":{"rightClicks":3,"captured":2,"empty":1,"ownWindow":0,"searches":1,"lastCapture":"…"},"hookActive":true}
```

| 字段 | 含义 |
|---|---|
| `hookActive` | 钩子装上了（`false` → 右键不会被接管，通常是安全软件拦的） |
| `rightClicks` | 钩子看到的右键次数（一直是 0 → 钩子没生效） |
| `ownWindow` | 被判为「在 DSH 窗口内」而放行 |
| `empty` | 右键了但没取到词（没选中，或 Ctrl+C 没送到） |
| `captured` | 成功取到词并弹了菜单 |
| `searches` | AI 搜索发起的次数 |
| `inApp` | 在 DSH 窗口内划词触发的次数（不在钩子统计里，走的是另一条路径） |
| `ticks` | 轮询在跑（可选功能用；一直 0 说明循环没起来，钩子也会一并失效） |

### 已知边界

- **只支持 Windows**。非 Windows 上插件会加载、设置页会说明不支持，但不会有功能。
- **全局钩子可能被安全软件拦截**。被拦时右键照常弹应用自己的菜单，功能等于没有 —— 设置页的「右键拦截」徽章会显示「未生效」。
- **剪贴板只还原文本格式**。富文本（HTML/RTF）和图片不还原 —— 翻一遍所有格式需要 `EnumClipboardFormats` 往返，等有人反馈丢了格式内容再说。
- **有任何修饰键按住时不取词**。取词靠注入 Ctrl+C，而用户手上正按着 Ctrl 时（他自己在 Ctrl+C / Ctrl+V），注入的和真实的那一对会串在一起：注入的 Ctrl-抬起会把用户的组合键提前结束，紧接着的剪贴板还原又把他刚复制的东西盖回去 —— 表现就是「复制粘贴不好用了」，而且是全应用范围的。所以只要 Ctrl / Alt / Shift / Win 有一个按着就放弃这次取词：代价是那一次右键不弹菜单，换的是不动用户手里的剪贴板。手动清单新增第 9 条守这个。
- **终端用 Ctrl+Insert**。有些终端两者都不支持，那种情况下取不到词（不会误发 SIGINT）。
- **`koffi.encode` 的最后一个参数是元素个数，不是字节数**。传字节数会写出两倍于分配的 UTF-16 单元、破坏堆 —— 短字符串靠对齐余量侥幸不崩，长文本必崩。改剪贴板相关代码后，手动测一次长文本（复制几千字再划词）确认没崩。
- **`UnhookWindowsHookEx` 返回成功不等于钩子已摘除**，摘除要等本线程处理完队列。`destroy()` 里因此先摘钩子、泵到摘除生效、最后才停泵 —— 顺序反了钩子会留下来继续吞全机的右键。手动清单第 8 条守的就是这个。
