# vyra-tool-usage-stats · 工具调用统计

按工具统计**调用次数、失败次数、最后使用时间**，并**记录失败原因**。数据来自会话日志本身，带设置页面板与 JSON 导出。

## 它回答什么问题

工具面优化的全部依据就是这几个问题，缺一个都做不了决定：

| 问题 | 靠什么答 | 只有它答会怎样 |
|---|---|---|
| 这个工具**用过没有** | 累计计数 | — |
| 这个工具**最近还在用吗** | 按日桶 | 拿累计当"最近在用"，**会删掉正在用的工具** |
| 它**为什么失败** | 失败审计（原因文本） | 只知道"失败了 181 次"，**不知道该修什么** |
| 这次窗口的**数据完整吗** | 覆盖范围行 | 把"数据从这天开始"读成"这段时间没干活" |

**这是本插件与"数一数调用次数"的区别所在。**

## 数据从哪来

监听 `session/event`，折叠持久化的 `tool/call` 与 `tool/result`。**没有独立的采集通道**，所以统计不可能和实际发生过的事不一致。

配对靠 `callId`，但两个事件的字段位置不同：

| 事件 | 工具名 | 配对 id | 结果状态 | 错误原因 |
|---|---|---|---|---|
| `tool/call` | `data.name` | `data.callId` | — | — |
| `tool/result` | — | `data.message.toolCallId` | `data.message.isError` | `data.error.reason` 或 `data.message.content` |

`tool/result` 的 id 在 **message 里**，不在事件顶层——这个差异如果搞错，统计会静默地永远是 0。

## 失败原因：两条路径都要读

失败有两种到达方式，**两个都得读**，否则整类失败归不了因：

| 路径 | 原因在哪 |
|---|---|
| 工具**返回**失败结果 | `message.content` 的文本块 |
| 工具**抛错** | 事件的 `error.reason` / `error.code` |

抛错路径的 `error.reason` 优先——它最具体，且刻意放在模型内容之外。

原因文本会**压成单行并截断到 300 字**。压单行不只是省空间：归因要按原因文本分组，多行文本会让同一种失败分裂成好几组。

每个工具保留最近 20 条失败。

## 两张表，两个口径，不互相兜底

- **累计计数** 答"用过没有"
- **按日桶** 答"最近还在用吗"

窗口查询（最近 7 天 / 30 天）**只读按日桶，永不回退到累计表**。累计数里大部分是历史，把它当"最近在用"就是上面表格里那个坑。

**累计计数永不裁剪**——"这个工具到底用过没有"是历史事实，裁掉等于改写历史。按日桶默认保留 90 天。

## 面板

**设置 → 工具用量**

| 元素 | 作用 |
|---|---|
| 统计范围下拉 | 累计 / 最近 7 天 / 最近 30 天 |
| 表格四列 | 工具 / 调用次数 / 失败 / 最后使用，列头可点排序 |
| 失败数按钮 | 点开看该工具最近失败的时间、错误码、原因 |
| 覆盖范围行 | 按日数据实际覆盖到哪天，以及保留多少天 |
| 导出 JSON | 下载完整数据，含 totals + failures，供离线分析 |

空态会区分原因：「还没有任何工具调用记录」vs「按日数据最早只到 X，更早的历史在『累计』里」——这两种情况在数据上长得一样，含义相反。

## 配置

```yaml
- id: vyra-tool-usage-stats
  name: 'vyra-tool-usage-stats'
  config:
    retainDays: 90                            # 每个工具保留多少天的日桶
    retainFailures: 20                        # 每个工具保留多少条失败样本
    endpoint: '/api/vyra/tool-usage'          # 读取端点
```

`endpoint` **必须**在 `/api` 前缀下：路由注册表拒绝任何它无法表达为共享 API 通道端点的路径，而那个拒绝发生在延迟 fiber 里，抛错不会显示在控制台。导出端点是它加 `/export`。

## 导出格式

```json
{
  "exportedAt": 1794495286746,
  "coverage": { "since": "2026-06-01", "until": "2026-11-12", "retentionDays": 90 },
  "totals": [{ "tool": "bash", "count": 142, "errorCount": 3, "lastUsedAt": 1794495286746 }],
  "failures": [{ "tool": "web_search", "at": 1794495286746, "code": "SEARCH_QUOTA", "summary": "quota exceeded" }]
}
```

## 设计约束

**统计永不影响工具调用。** 每条计数都包在 try/catch 里，失败只记日志。

**未知调用跳过而不是归到占位名。** 恢复的会话里，早期的 `tool/result` 可能没有配对的 `tool/call`（那些调用发生在本进程启动之前）。归到 `(unknown)` 会**凭空造出一个不存在的工具**。

**持久化写入不在工具调用路径上。** 每次调用都落盘会让一个会话写上千次；改为 15 秒定时刷。

**没有 storageDomain 时降级为纯内存。** 计数照记，重启清零。存储失败不阻止插件加载。

## 用法

```sh
node scripts/build.mjs        # 产出 lib/index.js (ESM) 和 lib/client.js (CJS，带 __ModuleLoader__ 包装)
node tests/check.ts           # 全部检查
```

客户端入口必须是 `window.__ModuleLoader__.load({ id, factory })` 形态——浏览器客户端模块系统这样执行它并注入 `require`。没有这层包装，页面会报 `module is not defined`，插件从不挂载。

## 已知限制

- **只统计本进程观察到的会话。** 在本插件挂载前结束的 Session，其事件不会被回放
- **没有按会话的 UI。** 端点返回 `sessions` 字段，面板只渲染全局视图
- **窗口视图不含失败数。** 按日桶只记调用次数，不含成功/失败拆分；窗口下的失败数显示为 0 而不是拿累计失败率充数
- **没有 Agent 维度。** 主 Agent 和子 Agent 调用同一工具会计入同一行
