# vyra-tool-usage-stats · 工具自进化

**让 DSH 的工具自己变好。**

它统计每次工具调用，**记下每次失败的原因**，定时把这些交给 Agent 诊断，给出**可一键应用的修复**——改描述、改参数、或说明实现该怎么改。

```
你的工具反复失败
        ↓
插件记下「失败了几次」和「为什么失败」
        ↓
定时（或你点一下）交给 Agent 诊断
        ↓
Agent 给出可直接应用的修复
        ↓
你点「应用」，工具就改好了
```

## 它解决什么问题

### 1. 减少重复报错

工具失败一次，模型往往重试同样的调用。插件把失败原因累积起来，交给 Agent 找出根因，**把"怎么做才对"写进工具描述**——下一次模型就知道该怎么用了。

真机验证的例子：

```
失败：read 工具报 FS_NOT_FOUND（读不存在的文件）× 若干次
  ↓ Agent 诊断
"diagnosis": "read 对不存在的路径直接失败，调用前未先确认文件是否存在"
"change": { "kind": "description",
            "description": "...Only call this tool on files you have verified
                            to exist: confirm the path with glob before reading,
                            and never issue speculative reads..." }
```

这不是泛泛的建议，是**能直接改进工具行为的文本**。

### 2. 节省 token

分析本身要花 token，所以插件在三个地方省：

| 做法 | 效果 |
|---|---|
| **按错误码分组**，同一种错只送 2 条代表样本 | 181 次配额失败 → 输入从 ~50K 压到 ~2K |
| **双门槛触发**：新增失败 ≥ N 次 **且** 距上次分析 ≥ T 天 | 单次偶发不分析；同一问题不反复问 |
| **分析过的记下来**，不重复问 | 反复问同一个已知问题 = 纯浪费 |

默认 `N=5`、`T=7天`，可配。

### 3. 看清工具在用没用、好不好用

| 视图 | 回答 |
|---|---|
| 累计 | 这个工具**用过没有** |
| 最近 7/30 天 | 它**最近还在用吗** |
| 失败 + 可展开的原因 | 它**为什么失败** |
| 覆盖范围行 | 数据从哪天开始（区分"没干活"和"没数据"） |

**累计和按日是两个口径，刻意不互相兜底**——拿累计当"最近在用"会删掉正在用的工具。

## 装上就会发生什么

1. **立刻开始统计**，无需配置
2. 每 24 小时（可调/可关）自动检查一次：有工具满足双门槛就交给 Agent 诊断
3. 诊断结果出现在 **设置 → 工具用量**，带前后对比
4. 你点「应用」→ **该会话的下一步**生效

## 配置

```yaml
- id: vyra-tool-usage-stats
  name: 'vyra-tool-usage-stats'
  config:
    # 分析门槛
    minFailures: 5        # 新增失败达到几次才值得诊断
    cooldownDays: 7       # 同一个工具隔几天才能再分析
    analyzeEveryHours: 24 # 自动检查间隔；0 = 只用「立即分析」按钮，最省 token

    # 数据保留
    retainDays: 90        # 按日数据保留天数（累计数永不裁剪）
    retainFailures: 20    # 每个工具保留多少条失败样本
```

**只想手动跑**：`analyzeEveryHours: 0`，然后用面板上的「立即分析」。

## 一键应用能改什么

| 类型 | 说明 | 安全性 |
|---|---|---|
| **描述** | 告诉模型怎么做才不触发这个错误 | 最高——不影响行为，只影响模型怎么用 |
| **参数** | 修正参数定义（JSON Schema） | 中——应用前会校验 schema 合法 |
| **实现** | Agent 只说明"该实现什么"，**不自动改代码** | 需要你手工落实 |

应用时会**保留原实现**（插件借用原 `execute`，不重写），并记录改动前的描述以便对照。

**应用不是立即的**：工具解析是作用域绑定的（实测：插件的 `ctx.tools` 返回 undefined，只有 agent 的 step 内才解析得到），所以改动排队到**该会话的下一步**执行。面板会写明这点。

## 面板位置

**设置 → 工具用量**

- 「立即分析」按钮 + 上次分析时间
- **自动分析设置**：检查间隔 / 触发门槛 / 冷却天数，改完即写入 profile 并重载
- 待处理建议卡片：诊断、依据、当前描述 vs 建议描述、「应用」/「忽略」
- 已应用改动列表
- 工具表格：调用次数 / 失败率 / 最后使用，列头可排序
- 失败数可点开，看每次失败的时间、错误码、原因
- 「导出 JSON」：完整数据离线分析

## 数据从哪来

监听 `session/event` 折叠 `tool/call` 和 `tool/result`——**日志里本来就有的事件**，所以统计不可能和实际发生过的事不一致。

失败原因有**两条路径**，都读：

| 路径 | 原因在哪 |
|---|---|
| 工具**返回**失败结果 | `message.content` 的文本块 |
| 工具**抛错** | `error.reason`（优先，最具体） |

只读一条会漏掉整类失败——这正是历史上某工具攒了 181 次失败却归不了因的原因。

原因文本**压成单行并截断到 300 字**：压单行是为了归组（多行文本会让同一种失败分裂成好几组）。

## 隐私与边界

- **完全本地**：数据存 `$DSH_HOME/storages/`，只有诊断请求会把**分组的失败摘要**发给模型
- **不自动改工具**：Agent 只出建议，应用必须你点
- **不阻塞工具调用**：所有统计逻辑都包在 try/catch 里，失败只记日志
- **实现改动不自动做**：只给说明，代码由你改

## 已知限制

- **只统计本进程观察到的会话**——插件挂载前结束的 Session 不会被回放
- **窗口视图的失败数来自按日桶**，按日桶从 0.2.x 起才有
- **没有 Agent 维度**：主 Agent 和子 Agent 用同一工具会合并到一行
- **应用延迟一步**：见上文"应用不是立即的"
- **诊断需要一个活跃会话**：请求靠 `agent/pre-step` 注入，所以「立即分析」会投递到你**已打开的那个对话**，下一个 step 生效。没有活跃会话时会明确提示，不会假成功
- **短任务需要退出前 flush**：headless 跑完即退的进程靠 `session/flush` 落盘（已修）

## 安装

在客户端「设置 → 插件 → 索引源」加入：

```
https://lanxiake.github.io/dsh-vyra-plugins/index.json
```

然后搜索「工具自进化」安装。**任意 0.2.x 版本都能装**（插件不声明 `engines.dsh` 限制，也不依赖任何 DSH 包，全部通过 `ctx.get` 在运行时读取）。

## 开发

```sh
node scripts/build.mjs        # 产出 lib/index.js (ESM) 和 lib/client.js (CJS)
node --test tests/counters.test.ts   # 单元测试
node tests/check.ts           # 全部检查
```

`check.ts` 需要 `dsh-Veyra` checkout（用 `DSH_SOURCE` 指定位置）。它跑：

| 检查 | 抓什么 |
|---|---|
| `counters` / `analysis` / `diagnose` 单测 | 纯逻辑，54 个用例 |
| `integration.ts` | 端点注册、计数器、审计、窗口、导出 |
| `storage.ts` | 存储域 spec、非法记录拒绝、旧数据迁移 |
| `session-e2e.ts` | 生产形状的事件折叠 |
| `boot-timers.ts` | **加载真实产物、跑过定时器**——抓"服务启动后崩溃"这类只有真跑才暴露的缺陷 |
